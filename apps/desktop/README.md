# EasyWork Desktop carrier

[中文](README.zh.md)

This package builds the Electron application and contains one bundled personal runtime Profile. Official DeepSeek Harness owns the Host, full Web Client and core execution; EasyWork feature packages supply shared experts, Skills, Library and MCP/connectors. These are the default owned feature boundary, not a promise that every definition or MCP service is preinstalled. The current Desktop supports a personal workspace only.

## Personal workspace

Opening the app prepares and starts the existing personal Home/Profile automatically, without a mode picker or enterprise login. The shared EasyWork account/model plugin signs in to `https://ask.vigoai.cn` and displays its model catalog. Its `ModelAdapter` uses the published DSH runtime; JWTs remain in Host credential records. Other official settings, the plugin manager, conversation, sidebar and right panel keep their official owners. Signing out preserves local data and explicitly installed plugins.

The main window loads the packaged official page before the local Host is ready and continues in that same document. Closing the window hides it while preserving background tasks, sessions, drafts and page state. Reopen through the Windows/Linux tray, the macOS Dock or another app launch. Application → Quit EasyWork, or Quit EasyWork in the tray, stops the Host and exits.

Window decoration follows official Desktop: Windows hides the system title bar and traditional menu bar, retaining native window buttons and Application / Edit menus in a 40px caption whose colors follow the page theme. macOS uses inset traffic lights and sidebar vibrancy. Empty caption space drags the window; fullscreen releases the caption clearance and reloads retain the current fullscreen state. On Windows, F11 toggles fullscreen and Esc returns to the normal window. Linux retains the official native window decoration.

The carrier bridges desktop shortcuts to the official client. The official shortcut protocol in the same published Profile manages preferences in `keybindings.json` under the Desktop user-data directory. The carrier contains no second DSH dependency tree.

Desktop provides no enterprise login, account authority bridge, member spaces, or company packaging configuration. Existing historical enterprise data is neither migrated nor deleted at startup. The terminal command always uses the personal space; its optional installation, repair, and removal are in the Application menu.

On first startup, when the personal Home has no workspaces or conversations, the default workspace on Windows is `%USERPROFILE%\Documents\EasyWork\default-workspace`. Desktop supplies the root through `EASYWORK_WORKSPACE_ROOT`; set it to an absolute path to use `default-workspace` beneath that root. Existing workspaces, conversations and historical directories are not migrated automatically.

## Windows updates and manual releases

Updater-enabled Windows x64 NSIS installations check their own channel after startup and every six hours without blocking offline work. Use **Application → Check for updates** to check manually. Updates download automatically while you work; the menu and taskbar show progress. Once verified, a bottom-right **Update ready** notice offers **Release notes**, **Restart and update**, and a dismiss button. Save drafts and finish active tasks before clicking restart. That click authorizes silent installation and automatic relaunch, without a second installer wizard. During installation, a small centered **Updating EasyWork** window in the app's UI language stays on top and closes as EasyWork reopens. The Application menu can still restart after dismissing the notice. Ordinary quit does not install an update. Before stopping the Host, restart revalidates the candidate version, size, SHA-512 and, for signed releases, publisher signature; missing or changed cache fails before shutdown and allows a fresh download. The carrier quits only after the installer process starts; process creation is not proof of successful installation. The update notice and manual check messages follow the startup page language and subsequent appearance changes without requiring the menu to open. Installation requires the Host's disposal acknowledgement, natural exit and confirmation that its Windows Job has no remaining descendants. A failed confirmation defers installation and asks you to restart before retrying. The official Host may terminate timed-out tasks during its own shutdown; a failed or forced stop never authorizes installation. Development, browser workers, unpacked directories, portable packages and ordinary unsigned local packages do not enable the updater. The explicit unsigned acceptance build below enables it.

`electron-updater` is pinned to **6.8.10**, with `autoDownload=false` and `autoInstallOnAppQuit=false`. The controller automatically downloads after discovery; the upstream auto-download setting stays off to preserve this ordering. Signed-mode download verification requires a valid timestamped Authenticode signature from the configured publisher, including cache hits; unavailable verification tooling blocks the update. Its dependency closure is bundled in `lib/desktop-updater.cjs`; the carrier still contains one official DSH Profile and no root runtime dependency installation. Channels are strict: `x.y.z-alpha.n` consumes only alpha, and `x.y.z` only stable (`latest`). Signed GitHub Releases use canonical `vVERSION` tags and the existing application/cache identity. Keep historical Setup and blockmap assets: the installed version's cached installer and old blockmap enable differential downloads. Missing cache, unavailable blockmaps or failed differential verification fall back to a full download through the updater. This optimizes download traffic; the complete EXE, ASAR, unpacked files and runtime are installed together. Existing versions without an updater need one normal installation of an updater-enabled version before A→B updates are possible.

The **Windows release** workflow is manual-only. Dispatch it from the default branch with a full source commit SHA, its already committed Desktop version and matching channel. `draft` verifies default-branch reachability and runs both Desktop and Web CI at that exact SHA. Native Windows x64 builds prepare one Profile/runtime, build only NSIS, sign the application/uninstaller/Setup, then verify timestamped publisher signatures, final SHA-512 and a recomputed blockmap. Existing carrier, archive closure, native registry, fuse and packaged-runtime gates remain active. An isolated-Home Windows GUI check opens the unpacked application, checks personal startup and project operations, and captures a screenshot. Only the complete verified asset set is uploaded to a Release draft; drafts cannot be discovered by clients.

From the repository root, `corepack yarn release:windows` dispatches `draft` after checking that `main` is clean and pushed. Before publication, use `corepack yarn release:windows --operation=publish --candidate-run=RUN_ID --acceptance-file=PATH`. The helper only dispatches the workflow; GitHub Actions still performs signing, actual acceptance and publication gates.

Without a signing certificate, run `corepack yarn release:acceptance` from the repository root. It requires clean, pushed `main` and a new alpha version, then dispatches **Unsigned Windows acceptance release**: build unsigned NSIS on Windows, verify the actual UI and Setup/blockmap/update metadata, run differential, missing-cache, corrupt-blockmap and offline-retry A→B scenarios against the newest unsigned baseline, then publish `acceptance-vVERSION`. The command waits for completion and prints the Release URL. Use `--no-wait` to dispatch only, or `--dry-run` to display the command. This entry point requires no certificate secrets; existing clients must use the same unsigned acceptance channel. After publication, the same run calls **Download release refresh**, which points the rolling `easywork-download` Release at the published installer as `EasyWork-x64-Setup.exe`. That Release is not a pre-release and is marked Latest while no stable release exists; updaters ignore its tag. Its installer is replaced only after the new upload matches the published digest. Its tag follows the default-branch commit that runs the refresh, because the workflow token cannot tag older commits once workflow files change; the installer's source commit stays on `acceptance-vVERSION`. To repeat or recover this step, dispatch **Download release refresh** manually with a published alpha version and its source commit.

The release workflows use no GitHub environments, so they create no deployment records. Configure repository Actions secrets `WIN_CSC_LINK` (PKCS#12 certificate, as accepted by electron-builder) and `WIN_CSC_KEY_PASSWORD`, plus repository variable `EASYWORK_WIN_PUBLISHER` matching the certificate's exact publisher name. Missing signing configuration blocks formal releases; unsigned local `package-win.ts` remains separate. Before building, both installer entry points check that the linked builder patch matches `yarn.lock` and contains the required NSIS safeguards. A stale dependency tree must be explicitly synchronized with `corepack yarn install --immutable` before an authorized release build. Builder signs before generating update metadata; do not modify or re-sign Setup afterwards.

The signed installer binds updates to the running executable's installation directory. It waits briefly for that installation's processes to exit naturally; unknown process ownership or query errors stop installation, and it never kills other EasyWork installations. Removal uses the newly signed uninstaller with the same directory/process checks, without running the older installed uninstaller. Launch, removal and checksum-locked 7za extraction errors stop installation. Replacement is in place with **no automatic rollback**. On installation failure, close EasyWork and run the complete signed Setup again to repair it. Personal Home, conversations, credentials, files and explicitly installed plugins remain outside the installer payload.

Publish with a **second manual dispatch**: `operation=publish`, the same source/version/channel, and the successful draft run's `candidate_run`. Supply `acceptance_json` with `sourceCommit`, `version`, `channel`, `installerSha512` copied from `release.json`, a repository issue/discussion `evidenceUrl`, and `checks` containing every key from [`ACCEPTANCE_CHECKS`](../../scripts/desktop-release-policy.mjs). Set each check to `true` **only after actually passing it**. Record required plugin UI, installed runtime, A→B and bytes transferred, missing-cache/full-download fallback, offline retry, corrupt-delta fallback, data retention, ordinary quit, busy shutdown, process cleanup and installer repair results with screenshots/logs. The publishing operator must inspect the evidence. The workflow compares every remote asset digest before making the complete draft public in one operation. It never replaces public assets or rebuilds a candidate for publication. Preserve old installer/blockmap assets and protect release tags. Keep repository-wide immutable releases off, because they would also freeze the rolling download Release. CI artifacts expire after 30 days, so publish within that window.

Acceptance explicitly distinguishes `mode: "bootstrap"` from `mode: "upgrade"`. The first updater-enabled release in each channel may use bootstrap: complete every `BOOTSTRAP_CHECKS` item, including a real normal installation over the old application and data retention. Put every remaining `ACCEPTANCE_CHECKS` key in `unperformed`, without marking it true. Authenticated, fully paginated release history must confirm there is no earlier updater-enabled public release in that channel; lookup failure blocks publication. Bootstrap does not claim A→B or differential acceptance. All later releases require upgrade mode and every upgrade check.

For prepublication A→B testing, use a disposable Windows VM, normally install signed baseline A, then download the exact signed draft B and baseline A asset sets (including each `release.json`) into separate directories. With the existing Web Playwright dependency available, explicitly run:

```powershell
node apps/desktop/tests/acceptance/accept-windows-update.mjs --confirm-isolated-vm --app="C:\Users\tester\AppData\Local\Programs\EasyWork\EasyWork.exe" --home="C:\tests\fresh-home" --output="C:\tests\results" --baseline="C:\tests\A" --candidate="C:\tests\B" --scenario=delta
```

This opens installed A with a fresh test Home and redirects only that inspected process's GitHub discovery and updater sessions to a loopback fixture. It preserves app versions, signed bytes and signature verification; it never changes the production feed. Create representative local test data and finish tasks in that Home before clicking the real update notice or restart menu action. The tool records completed payload bytes and range requests. Close any automatically relaunched B: the installer may relaunch through the Windows shell without A's process-only test Home setting. Then rerun the same command with `--verify-installed` appended, keeping the same `--app`, `--home` and other arguments. This mode reuses the existing test Home, asserts B's actual version and user-data path, records `installed-observation.json`, and opens B for manual data/UI inspection. Only compare data in this verified Home; screenshots, data preservation and process cleanup still require actual operator checks. Restore the VM snapshot between scenarios. Repeat with `missing-blockmap`, `corrupt-blockmap` and `offline`; type `online` and Enter to restore the offline fixture before retrying. For missing-cache testing, remove only A's cache in the disposable VM (`%LOCALAPPDATA%\<updaterCacheDirName>` from `release.json`) before running the delta scenario. Retain cache for a real differential test. The fixture is an acceptance tool, not proof that these scenarios have passed; it does not automatically approve evidence or install until you choose the real restart action.

Non-building implementation checks are `corepack yarn typecheck` and `corepack yarn check:updates`. Small synthetic byte fixtures run the actual pinned differential downloader and verify Range reuse, reconstructed SHA-512 and full-download fallback for missing cache, corrupt blockmaps and corrupt cached bytes. Headless checks also cover candidate revalidation, launch ordering, PowerShell progress/error handling and language synchronization. These checks do not execute NSIS or establish real application A→B behavior, savings, outage recovery, data retention or UI acceptance. Build, runtime preparation, signing, packaging, CI dispatch and installation remain explicit operations. Use the exact release’s Windows acceptance artifact for measured installation results and remaining unverified scenarios.

Without a Windows signing certificate, explicitly build an updater-enabled acceptance installer with `corepack yarn build:win --target=installer --acceptance-updates --skip-install`. It requires clean default-branch source and an alpha version. Windows TESTSIGNING is unnecessary; Windows may identify the unsigned application as an unknown publisher. This mode accepts only `acceptance-vVERSION` prereleases and uses HTTPS GitHub metadata, exact size and SHA-512 verification; it does not authenticate an Authenticode publisher. The signed stream retains mandatory publisher verification. Both modes use the same safe shutdown and NSIS installer. Ordinary unsigned packaging remains updater-disabled.

For manual debugging or review, run `node apps/desktop/tests/acceptance/accept-windows-package.mjs --local --unsigned-updates`, then `node apps/desktop/scripts/stage-unsigned-windows-release.mjs`. The `release:acceptance` entry point creates the draft, runs the four **Windows update acceptance** scenarios against the newest unsigned baseline, and publishes the already tested bytes after all evidence passes. No candidate run ID or acceptance JSON needs to be entered manually. This does not claim signed-publisher validation, live account credentials or arbitrary external-plugin retention. Existing updater-disabled versions, including alpha.5, require one manual installation of A. Preserve earlier Setup/blockmap assets for subsequent differential updates.

## Development and validation

Startup diagnostics are written locally to `logs/startup.log` under the Desktop user-data directory (`%APPDATA%\EasyWork` on Windows). They record Host and plugin-loading stages, elapsed time, resource status and loading progress; while startup is pending, a waiting record is added every five seconds. Files rotate at 2 MiB with three backups. Runtime output is stored as metadata summaries; request bodies, authentication headers and conversation text are not recorded. Fatal exceptions retain a small `startup-fatal.log` metadata record in the user-data directory.

Packaged Desktop stores its single Profile in `app.asar/profiles/easywork` and starts the official Host with Electron's Node mode and `--expose-internals`. JavaScript and manifests retain their published bytes inside the archive; native binaries and Office engine resources remain unpacked. The supported Electron version is pinned with the carrier. Startup does not pre-read the entire module tree. `app.start.osUptimeSeconds` records seconds since system boot; warm launches do not replace acceptance of the first launch after restarting the computer. For per-plugin diagnostics, create an empty `startup-trace.enabled` file in the same `logs` directory. The next launch also writes `host-startup-*.json` and `.cpuprofile`; remove the marker after diagnosis to stop sampling.

Use Node.js `^22.19.0` or `>=24` and Corepack Yarn 4.18.0. At the repository root:

```sh
corepack yarn install --immutable
cd apps/web
corepack pnpm install --frozen-lockfile
corepack pnpm build
cd ../..
node apps/desktop/scripts/pack-easywork-profile.mjs apps/web
corepack yarn dev
```

`dev` builds the carrier, prepares its pinned Profile and primary runtime, then launches Electron. The Web build runs each selected package and its dependencies once; a package's own `build` command also prepares its dependencies. Primary-runtime and Office preparation reuses identical files. Private build receipts let later runs reuse verified file pairs when their identities, sizes, modes and modification/change times match; missing or changed files are compared and repaired as needed. Receipts are not shipped or used as release integrity evidence. Python, Office, skills and the existing checksum and packaged-runtime gates remain intact. Keep graphical launch explicit. Headless verification uses:

```sh
corepack yarn typecheck
corepack yarn check:bilingual-docs
corepack yarn check:desktop-dsh-alignment
```

`corepack yarn check` is the full headless gate. `corepack yarn workspace dsh-plugin-desktop package:dir` creates an unpacked application and checks for duplicate DSH trees. Build and type checks do not establish real window, packaged-runtime or server acceptance.

Windows installer performance can be compared with `node apps/desktop/scripts/build-windows-nsis-ab.ts --label=candidate`. It builds direct-extraction and staged-copy installers from the same unpacked application without changing the repository's builder patch. Run it separately in baseline and candidate worktrees, then use `apps/desktop/scripts/run-windows-nsis-ab.ps1` with their manifests. For cold measurements, prepare one canonical VM snapshot and restore it before each variant and scenario; alternating runs on a warm system does not establish cold-install or upgrade performance. Keep generated manifests, measurements and screenshots in local artifact directories.

`corepack yarn release:pack` builds and packages the same commit's Web sources and the reviewed Desktop composition, preserving the clean-source release gate. The Web release directory also receives `desktop-release-manifest.json` and its hash-named archives for published Desktop packaging.

Build the five owned features and their required support packages in EasyWork first. `pack-easywork-profile.mjs` creates immutable archives and a version/hash manifest in `build/easywork-profile-release`; select another candidate with `EASYWORK_RELEASE_DIRECTORY`. Runtime preparation installs the official version with a portable lockfile and carries pnpm's JavaScript CLI for explicit plugin operations. It rejects additional default feature packages and verifies the real plugin manager exposes exactly five EasyWork bundles. The same Profile preserves the pinned SkillHub 0.2.16 and dshmarket 1.66.8 catalog integrations. Their catalog entries are not all installed or reviewed by EasyWork. It does not package a live user's configuration or credentials.

The release Profile uses pnpm `nodeLinker: hoisted`: Windows installer archives expand dependency links into repeated files, so both preparation and `afterPack` reject virtual package stores or linked package directories. Nested official dependencies still undergo the exact DSH version gate. Packaging excludes dependency source maps, type declarations and PDB debug files, while retaining runtime binaries, Office assets, skills and licenses. This changes only the bundled release layout; the root Yarn workspace and Web pnpm workspace keep their own settings. To prepare an isolated Profile candidate, set `EASYWORK_RUNTIME_DIRECTORY` to a dedicated directory inside `apps/desktop/build`; the packaging pipeline continues to use `build/easywork-runtime`.

Product-owned packages, development variables, data directories and storage keys use `easywork-*`, `EASYWORK_*` and EasyWork. The carrier uses the `easywork` Profile without aliases, fallback paths or migration of retired product data. `corepack yarn check:naming` rejects retired names in source and file paths without exceptions.

Web and Desktop Profile packaging also checks names inside the compressed plugin archives and release metadata. Desktop `afterPack` starts an isolated, headless runtime to inspect the actual native Skill commands and MCP tool schemas. Run `node apps/desktop/scripts/verify-runtime-product-names.mjs <runtime-directory>` from the repository root to repeat that check for a prepared or packaged runtime; it does not open a window or send model requests.

The Desktop pin and shared product target are **DSH 0.2.1-rc.2**, selected explicitly by the user. The unmodified official `dsh-v0.2.1-rc.2` tag pins commit `687f282e8625c6b8d11ff58211a90524be2e4317`. Existing installed applications and Profiles have their own actual versions. Desktop alignment, Desktop checks and packaged-runtime acceptance must pass before declaring the unified upgrade complete; Web Docker evidence cannot replace those gates. Prefer validated official stable releases by default.

Builds consume only published official packages and checksum-locked binary artifacts. The carrier source and packaging scripts live here; feature package source belongs to EasyWork, and apps/web owns Web launch and deployment. See [Desktop ownership](../../docs/desktop-boundaries.md).
